# FastDL spec

Personal download manager modelled on how Internet Download Manager works (from public knowledge; no reverse engineering, no license bypass).

## Non-goals
DASH audio+video merging for sites other than YouTube, DRM, torrents, FTP, site grabber. (Proxy: HTTP and HTTPS proxies only, settings.proxy; SOCKS is out.)

## Download File Info flow (IDM's confirm window)
- **Entry points.** Every Download click in the browser: the extension's video button, browser-download takeover, "Download with Glide" context menu, and the popup's Download this video and media-list buttons. They call `sendConfirm()` (`common.js`), which sends `POST /api/add` with `confirm: true`. The engine answers `{id}` at once with the download in status `pending`, and starts a quick probe. The native app sees the new pending download in `/api/state` and shows its Download File Info dialog for it; the browser opens no window. The engine refuses `confirm: true` with 503 while the native app is not open (see HTTP API), and a refused taken-over download goes back to the browser. A link pasted in the native app goes the same way.
- **Pending.** `pump()` never starts it; the native app hides it from the list, sidebar counts and toolbar. It is never saved (`state.json` leaves it out), `load()` drops any, and `tick()` drops those older than `pendingMs` (30 min), so a window closed with its X leaves nothing behind.
- **Probe** (`probe()`, fills `d.probe = {name, category, size, type, error}`). http: `GET` with `Range: bytes=0-` through `Manager.get()` (cookies stay on their host, 15 s limit for the headers); a usable answer stays open and unread in `mgr.held` (memory only, never in `state.json`), anything else is cancelled; name from Content-Disposition, else the final URL; size from the Content-Range total, else Content-Length; the MIME type. A failure keeps the URL's name and the error, which the window shows as an amber note. HLS: the URL's name; `parsePlaylist()` (15 s limit) makes it `.mp4` for `#EXT-X-MAP` or a separate sound track, else `.ts`; a failure keeps `.ts` and the error. Video: first `listing: true` with the tab title (without a leading "(3) " and a trailing " - YouTube") as the name, then `formats()`: the real title (also kept as `d.title`) plus the extension of the picked key (`extOf()`), `options`, `format` (the preset key if the list offers it, else mp3 for quality mp3, else the first MP4, else the first option) and its size; a list error keeps the tab title, `options: []` and the error. The download's own name or title wins as in `assignName()`. Category from the extension (`settings.types`, else Other; an open window's `probe.category` follows a change of `settings.types` at once). **Duplicate:** when another download in the list (not pending, not being removed) has the same url, the probe also gets `duplicate: {id, name, status}` of that one (set with the first probe values and again when the probe ends; see Duplicates).
- **Window** (the native app's Download File Info dialog, `docs/NATIVE_UI.md`). URL (selectable), amber note, Format (YouTube: optgroups MP4 / WEBM / Audio, each option with its real size; "Getting formats…" while listing, when only Cancel works; "MP4 · best quality" / "MP3 · audio" (legacy `best`/`mp3`) when the list failed), Category, Save As with Browse…, Size (the format's size; "Known once the download starts" for YouTube without one, "Unknown" without a size). Save As starts as `<dir>\<Category>\<name>`; Category rewrites the folder (the remembered `settings.folders[<Category>]` first, else `<dir>` itself for Other or when `settings.categories` is off, as `assignName()` does); Format swaps the extension (`.mp4/.webm/.m4a/.mp3`), Video/Music (m4a and mp3 are Music) and the size. Start sends `format` (a listed key) or `quality` (legacy). **Format already picked:** when the pending download has its own `format` (the extension's format menu; `probe()` deletes it when the list does not offer it) and the probe is still listing or its `options` contain that key, the whole Format row is hidden and the gap closed; Start/Later send that key, Size shows its size, the name already has its extension. Otherwise (pasted link, popup, context menu, or a format no longer offered) the Format row shows as above. **Remember this folder for <Category>** (checkbox under Save As, "for other files" for Other; unchecked every time the window opens; "Missing folders are created." is Save As's tooltip): when checked, Start and Download Later send `remember: <Category>`. Category's **+** opens the category editor and selects the new category. **Description** (optional, 300 characters) is sent with Start and Later. Start Download (Enter) turns the dialog into the progress window; **Download Later ▾** opens the Add to queue popover (a queue, + for a new one, "Start the queue now") and sends `later` with `queue` and `startQueue`; Cancel (Esc) closes it. Server errors show under Save As. When `probe.duplicate` comes (often after the window opened), the app asks with its Link already in the list window, or applies `settings.duplicates` (see Duplicates).
- **`confirm(id, {action, path, quality, format, remember, description, replace, rememberDuplicates, queue, startQueue})`** (async). Only for a `pending` download. `rememberDuplicates` (`number` | `replace` | `resume`) is saved in `settings.duplicates` first, also on `cancel` (the app's answer for "resume the existing one"). `cancel` removes it. `start` → `queued` with `notify: true` (the app shows its Download complete window for it). `later` → `scheduled` in `queue` (default `main`; an unknown id is an error; a queue removed while the call waited gives `main`); `startQueue` starts that queue. `description` is cleaned as in Downloads' own fields. `replace`: the id of the duplicate (see Duplicates). `path` must be a full Windows path (drive or `\\server\share`) ending in a file name; the name goes through `sanitize()`, video gets `extOf(format, quality)`; `format` must match `FORMAT_KEY` and be in the video's list (fetched again when the cache expired), else "unknown format"; a legacy `quality` clears `format`; the folder is created, and a taken name (file, `.fdl`, or another download's) gets ` (n)`. Sets `file`, `name`, `tmp`; `assignName()` keeps a preset `file`, so http, HLS and video all write there. `remember`: a category name (a key of `settings.types` or `Other`) stores `settings.folders[remember] = dirname(file)` for start and later; any other value is ignored. **Folder rule** (`assignName()`, for every download without a chosen path: Add links, scheduled, the extension without the window): `settings.folders[<category>]` when set (also with `categories` off), else `<dir>\<Category>` when `categories` is on and the category is not Other, else `<dir>`.
- **Browse…** Windows' own `SaveFileDialog` in the native app (no overwrite prompt: names get numbered instead).
- **Progress window.** In the native app, see `docs/NATIVE_UI.md`.

## Download engine (`engine.js`)
- **Probe = first connection.** `GET` with `Range: bytes=0-`. 206 + `Content-Range` total, or 200 + `Accept-Ranges: bytes` + length → resumable. The probe's body keeps streaming as segment #1. After the Download File Info window, the held probe response is that first response (IDM's trick): Start makes no new request and the other connections start at once; a dead one goes through the normal retries. Cancel, Later, Pause, remove, a new address, pending expiry and quit close it (`release()`; `tick()` also lets go of one whose download no longer waits to start). 416 → asked again without `Range` and downloaded as not resumable (zero-byte files). 5xx and 429 are retried up to 4 times; a numeric `Retry-After` (capped at 30 s) replaces the default backoff.
- **Dynamic segmentation.** Up to `settings.connections` connections per download. A free connection first takes an unstarted/unfinished piece; otherwise it splits the largest active piece in half (only if each half keeps ≥ 512 KB). A piece shrinks under a running connection, which stops at the new end.
- **Resume.** Each retry asks for `bytes=pos-end` and must get 206 with `Content-Range` starting at `pos` and the same total; anything else is an error (file changed on the server).
- **Not resumable.** One connection; every retry, pause or restart starts over from byte 0.
- **Failures.** A connection retries up to 5 times (2 while others are alive). When it gives up while others are alive, it is retired and the download carries on with fewer connections (servers that cap connections per user). No data for `stallMs` (30 s) cuts a connection off. **Takeover:** when a piece's connection has heard nothing for `staleMs` (5 s; time spent in our own speed limit does not count) while a connection slot is free, a fresh connection takes its whole remaining range (`pos`→`end`, however small) and the silent request is cut; checked every second and whenever a connection ends. Its old worker ends at once, without a retry or lowering the connection count. Single-connection and non-resumable downloads keep only the 30 s watchdog.
- **Files.** Written into `<name>.fdl` (preallocated), renamed when complete; `segments` are then dropped from the state. Names: `Content-Disposition` → URL → `download`; `sanitize()`; duplicates get ` (n)`; optional category subfolders (the category's name, from `settings.types`).
- **Queue.** At most `settings.maxActive` downloads run; others wait as `queued`. `pump()` goes down the list in order; a download of a running queue also waits while that queue already runs its own `maxActive`. A queue that is not running holds nothing back: a download resumed by hand runs. Named queues and their schedules: see Queues.
- **Speed limit.** One global debt-based token bucket across all connections, rate `speedLimitOn ? speedLimitKB * 1024 : 0`. Each download also has its own bucket (`limitKB`); a chunk waits for both (`take()`), read per chunk, so a change applies at once for HTTP and HLS.
- **State.** `state.json`: settings + list. Saved atomically every second while anything runs or changed. On load: `downloading` → `queued`; a `scheduled` download without a queue goes into `main`; a queued download of a queue → `scheduled` (no queue runs after a restart); a queue id that no longer exists → `main`.
- **Pause all** (tray, command bar). `pauseAll()` stops every running queue (their downloads go back to `scheduled`), pauses the other `downloading` and `queued` downloads and aborts running ones without a `pump()`, so no queued download starts in between. `scheduled` downloads keep their queue and start time.
- **Power: the one countdown.** One `powerDelayMs` (60 s) countdown (`powerAt`), started by three triggers; `powerOp` says what it does, `powerAll` whether it is "When all downloads finish":
  - **When all downloads finish** (the status bar). `whenDone` (`sleep` | `shutdown` | `''`) lives in memory only and is used once, so a forgotten "shut down" can't fire days later or after a restart. Work = `downloading`, `queued`, a `scheduled` download whose queue runs or has a start time, or a queue retry that waits; paused and failed downloads don't count. On the tick after the last work ends, the countdown starts (`powerAll: true`); a download that started and ended between two ticks still counts (`worked`). New work stops it, and it starts again when that work ends. At zero, `whenDone` goes back to `''`.
  - **A download's own `whenDone`** `sleep` / `shutdown` when it completes, and **a queue's `whenDone`** when that queue is done: the countdown starts (`powerAll: false`) even while other downloads run. New work does not stop it, and the status bar's choice stays when it fires. A download's own `open` calls `opener(d)` instead.
  - `POST /api/settings {whenDone: ''}` (Cancel) stops any running countdown at once. At zero, `power(op)` runs. `power` and `opener` do nothing in `engine.js`; `server.js` sets the real ones, so tests and other users of `Manager` can't switch the PC off or open files.

## Downloads' own fields (`engine.js`, all in `view()`)
- **`description`**: text, control characters removed, trimmed, at most 300 characters; null when empty. Set by `add({description})`, `confirm({description})` and `POST /api/action {op: 'describe', id, description}`.
- **`limitKB`**: this download's own speed limit, 0–10 000 000 KB/s, 0 = none. `POST /api/action {op: 'limit', id, kb}`. HTTP and HLS apply it at once; YouTube gets yt-dlp `--limit-rate` with the lower of the two limits (the global one only when on) from its next run.
- **`whenDone`**: `''` | `open` | `sleep` | `shutdown`, what happens when this download completes (see Power). `POST /api/action {op: 'whenDone', id, value}`; any other value is `''`.
- **`lastTry`**: the time of the last start (`start()` sets it). `finished` stays the completion time.
- **`notify`**: true once the download was started from the Download File Info window (`confirm` `start`). The app shows its Download complete window once when such a download completes (when `settings.showComplete` is on); the app remembers which ones it showed, the engine only keeps the flag.
- **`queue`**: the id of its queue, or null (see Queues).
- **`segments` in `view()`**: `[start, end, pos, active]`; `active` is 1 while a connection works on that piece, else 0 (the progress window's Connections table).
- **`referer` in `view()`**: the download's Referer header, or null (Properties). Cookies never leave the engine.

## Duplicates (`engine.js`)
A duplicate is a download whose url equals one already in the list (not pending, not being removed).
- With the window (`add({confirm: true})`): `probe.duplicate = {id, name, status}`. The app asks (`settings.duplicates` `ask`, its Link already in the list window) or applies the saved choice, then answers through `confirm`:
  - `number`: a normal `start` / `later`; the new file gets ` (1)` etc. as usual.
  - `replace`: `confirm({…, replace: <existing id>})` removes the existing entry first (its `.fdl` and temp files too). When Save As is still the existing file's path, the new download writes there: the old file stays until the new one finishes and its final rename writes over it. Another path: the old entry still goes and the new file is numbered as usual. The app sends `replace` only while Save As is the existing file.
  - `resume`: the app sends `confirm({action: 'cancel'})` for the new one and resumes the existing one (`act 'resume'` when it is paused, failed or scheduled); a finished one is shown instead (its Download complete window), a running or waiting one gets its progress window.
  - `rememberDuplicates` saves the choice in `settings.duplicates`.
- Without a window (Add links, batches, `scheduled`): `ask`, `number` and `resume` number the new file; `replace` removes the existing entry, and the new download takes its file path once the old temp files are gone.

## Queues (`engine.js`; the app's Scheduler)
- **`settings.queues`**: an array; the first is always `{id: 'main', name: 'Main download queue'}`, which can't be removed or renamed (the app shows it as "Main queue"). Each queue: `id` (made by the engine), `name` (1–40 characters, control characters removed, unique regardless of case), `maxActive` (1–20, default 1: files at the same time), `startAt` (`''` or `HH:MM`), `days` (0–6, Sunday = 0, sorted, no repeats; empty = every day), `stopAt` (`''` or `HH:MM`), `retries` (0–10, default 0), `whenDone` (`''` | `sleep` | `shutdown`). Wrong values fall back to the default. `load()` drops broken or doubled entries.
- **In a queue.** A download in a queue that waits for it has status `scheduled`. Its place in the queue is its place in `mgr.list` among that queue's downloads. `POST /api/action {op: 'queue', id, queue}`: into a queue (paused, failed and queued downloads become `scheduled`, a running one keeps running; pending, finished and removed ones are refused), or `queue: null` out of every queue (`scheduled` becomes `paused`). `{op: 'up' | 'down', id}` swaps it with the previous / next unfinished download of the same queue (finished downloads keep their queue but are skipped, and can't move). `add({scheduled: true, queue})` (default `main`) and `confirm({action: 'later', queue, startQueue})` put a new download into a queue.
- **Runs** (`mgr.runs`, never saved: after a restart no queue runs). Start (by hand, or `startAt` on an allowed day): the queue runs and `pump()` turns its `scheduled` downloads into `queued`, also ones added while it runs. Stop (by hand, or `stopAt`): its downloading and queued downloads go back to `scheduled` (aborted like Pause, but they stay in the queue).
- **Scheduler tick** (`tick()`, every second, also with a test clock): a queue starts when the clock's HH:MM equals `startAt` on one of its days (every day when `days` is empty) and stops at `stopAt` (any day, only while it runs). Each start and each stop fires once a day per queue (`fired`), so a start or stop by hand in that minute sticks.
- **Retries.** While a queue runs, a failed download of it goes back to `queued` 10 s later, up to `retries` times per download in that run. A waiting retry keeps the queue running.
- **Done.** A running queue with nothing `queued`, `downloading` or `scheduled` left and no waiting retry stops; if it started something in that run, its `whenDone` starts the countdown (see Power). A queue started with nothing in it ends without its `whenDone`.
- **API.** `POST /api/queues {op: 'add', name, …fields}` → `{id}`; `{op: 'update', id, …fields}` (the main queue's name can't change); `{op: 'remove', id}` (not `main`; a running queue stops first; its downloads go to `main`); `{op: 'start', id}`; `{op: 'stop', id}` → `{ok: true}`. `POST /api/settings {scheduleAt}` still sets the main queue's `startAt` (older apps); `queues` there is ignored.
- **`view().queues`**: each queue's fields plus `running`, `waiting` (scheduled + queued), `active` (downloading) and `total` (all its downloads, finished ones too).
- **Migration on load.** The old `scheduleAt` becomes the main queue's `startAt`; `scheduled` downloads without a queue go into `main`.

## Categories (`engine.js` `settings.types`)
- `settings.types`: `{name: [file type, …]}` in sidebar order; default `CATEGORIES`: Video, Music, Programs, Documents, Compressed. It is used everywhere a category is needed: the probe, `assignName()`, `isCategory()` (with `Other`), `view().exts` and `view().categories`.
- The five built-ins are always there, first, in that order (the app keys their icons by name): they can't be removed or renamed; their file types and folders can change, and one left out of a POST keeps its types.
- Custom categories: a name of 1–30 letters (any script), digits, spaces, `-` or `_`, no leading or trailing space, unique regardless of case, not "Other" or "All". They can be added, renamed and removed. A rename is a custom name that disappears while a new one takes its place in the order: its remembered folder follows (unless the same POST sends `folders`). A removed one's downloads become Other (categories come from file names) and its folder entry goes.
- File types: 1–10 lower-case letters or digits, without the dot; a bad one is dropped on its own. One category per type: the later one in the POST wins.
- Folders stay in `settings.folders` per category.

## HLS (`hls.js`)
Master playlist → highest `BANDWIDTH`. **Separate sound** (X serves video and sound apart): when that variant's `AUDIO` group has `#EXT-X-MEDIA:TYPE=AUDIO` tracks with a `URI`, the group's `DEFAULT=YES` track (else its first) is downloaded too; a track without a `URI` is inside the video already. AES-128 with explicit IV or media-sequence IV; other methods are refused as DRM. `#EXT-X-BYTERANGE` playlists are refused. Segment bodies are read chunk by chunk under the stall watchdog. `#EXT-X-MAP` or a separate sound track → `.mp4` output, else `.ts`. Segments fetched `connections` at a time, written in order, one track after the other: video into `d.tmp`, sound into `<file>.audio.fdl`. `d.hls = {done, bytes, total, parts: [{done, bytes}]}`: totals over both tracks for the UI, `parts` per track; resume continues at each track's first unwritten segment (older state without `parts` starts over). Then ffmpeg (`ffmpegExe()`, looked up before anything downloads, so a missing ffmpeg fails at once with the winget hint) copies both into `<file>.join.fdl` (`-map 0:v:0 -map 1:a:0 -c copy`, `-f mpegts` for a `.ts` name, else `mp4`) with `phase: 'merging'`; that file becomes `d.file` and the temp files are deleted (`remove` deletes them too). A pause during the join kills ffmpeg and waits for it to exit; resume joins again.

## Video sites (`ytdlp.js`)
- **URLs.** `youtube.com`, `www.`/`m.`/`music.youtube.com` with `/watch?v=`, `/shorts/`, `/live/`, `/embed/`, and `youtu.be/<id>`. The 11-char ID is required; channels and playlists are refused. Stored as `https://www.youtube.com/watch?v=<id>`, kind `video`, no headers or cookies.
- **Format list** (`listFormats()`, `formatOptions()`). `yt-dlp -J --no-playlist --ignore-config --no-warnings --extractor-args youtube:skip=hls,dash` (2 min limit; the skip leaves out the stream manifests, unused because only https formats are offered, about 0.6 s less), cached 15 min per video id in `mgr.formatCache` (callers during a run share it; a failure is not cached). Live → refused. Options `{key, group: MP4|WEBM|Audio, label, tag?, size}`: https formats only; video-only SDR mp4/webm of at least 144p (the short side, so shorts say 1080p), one per height, best first, H.264 preferred in MP4; paired with the best m4a (MP4) or webm/opus (WEBM) audio; label `720p`/`1080p60`, tag HD (720–1080), 2K (1440), 4K (2160). Audio: M4A (best m4a) and MP3. **Sizes are real:** yt-dlp's `filesize`, else `exactSize()` (a `Range: bytes=0-0` request with the format's own headers, no cookies, 15 s, the Content-Range total of a 206); a format with neither is left out; MP4/WEBM = video + audio; MP3 = duration × 192 kbps / 8 (constant bitrate). Measured on a 19 s video: MP4 144p shown 504,566 B, file 506,017 B; MP3 shown 456,000 B, file 457,388 B (merging and the MP3 header).
- **Recordings YouTube is still processing** (`live_status: post_live`, just after a live stream). Every format is `http_dash_segments` (pieces), even with skip=dash, and neither yt-dlp nor the page has an exact size. Those formats are offered with yt-dlp's `filesize_approx` (no range request) and their options get `approx: true`, shown with "~" ("~1.04 GB") in the extension's menu and the app. `optionsFromPlayer()` gives [] when the page has video formats but none with a size, so the extension uses the app's list (before, it showed MP3 alone). yt-dlp gets `-N <settings.connections>` (pieces at once; single-file formats are unchanged), `-N 1` while a speed limit applies, because `--limit-rate` holds per piece.
- **Format → args** (`formatArgs()`). Keys (`FORMAT_KEY`): `mp4:<v>+<a>`, `webm:<v>+<a>` → `-f <v>+<a> --merge-output-format mp4|webm`; `m4a:<a>` → `-f <a>`; `mp3` → `-f ba/b -x --audio-format mp3 --audio-quality 192K`. A key is checked against `FORMAT_KEY` in `add()`, `confirm()` and `formatArgs()`, and against the video's list in `confirm()` and before yt-dlp starts ("This video no longer offers the format …"). Legacy `quality` `best|1080|720|480|mp3` (default `best`; anything else is refused in `add()`), used when there is no `format`: video `-f bv*+ba/b -S res[:N],vcodec:h264,ext:mp4:m4a --merge-output-format mp4` (H.264 preferred at equal resolution); mp3 as above. Always `--ignore-config` (a user config could add cookies or change output names), `--no-playlist`, `--match-filter !is_live`; `--limit-rate` with the lower of the global limit (only when `speedLimitOn`) and the download's own `limitKB`, fixed per run.
- **Files.** yt-dlp writes into `<dir>\.fastdl\<id>` as `media.<ext>`. On success the file is moved to its final name (`assignName()` with the title, unique ` (n)` names, categories → Video/Music), the temp folder is removed (and `.fastdl` once empty), and Mark-of-the-Web is set.
- **Progress.** Parsed from yt-dlp's stdout/stderr lines: `FDLINFO` (format ids, expected size, title), `FDLP` (per-stream bytes; `streams` keeps `{got,size}` per format so the bar does not restart), `FDLPP` (post-processor), `FDLFILE` (final path). `phase`: `video`, `audio`, `merging` (Merger), `converting` (ExtractAudio).
- **Pause/resume.** Pause kills the whole process tree (`taskkill /T /F` on Windows, process group elsewhere: yt-dlp.exe is a launcher and ffmpeg may run). Resume re-runs yt-dlp, which continues its `.part` files.
- **Tools.** yt-dlp: `FASTDL_YTDLP`, `%LOCALAPPDATA%\Microsoft\WinGet\Links`, WinGet `Packages\yt-dlp.yt-dlp_*`, then PATH (other apps put old copies there, and YouTube refuses an old one). ffmpeg: `FASTDL_FFMPEG`, PATH, WinGet `Packages\yt-dlp.FFmpeg_*\ffmpeg-*\bin`. Missing tool → error with the `winget install` command.
- **Errors.** First `ERROR:` line, non-zero exit or no file → error plus the hint `winget upgrade yt-dlp.yt-dlp`. Live streams → "Live streams are not supported". Cookies are never passed to yt-dlp.

## Data model
Download: `id, url, name, title, headers{cookie,referer,user-agent}, cookieHost, kind(http|hls|video), status(pending|queued|downloading|paused|done|error|scheduled|removed), file, tmp, size, resumable, segments[{start,end,pos}], hls{done,bytes,total,parts[{done,bytes}]}, error, added, finished, lastTry, description, limitKB, whenDone('' | open | sleep | shutdown), notify, queue(queue id or null), probe (pending only: name, category, size, type, error, duplicate?, and for video listing, options, format)`; video only: `quality, format, phase, got, streams{format_id:{got,size}}, tmpDir`; HLS: `phase` (`merging`) while ffmpeg joins a separate sound track.
Settings: `dir, connections(1–32, 8), maxActive(1–20, 3), speedLimitKB(0–10 000 000), speedLimitOn(bool, off; a loaded state with speedLimitKB > 0 and no speedLimitOn gets true), categories(bool, on), clipboard(bool, off), folders({<Category or Other>: absolute folder}, {}), types({<category>: [file types]}, see Categories), duplicates(ask | number | replace | resume, ask), showComplete(bool, on), queues([…], see Queues)`. `update()` checks what a POST sends; `speedLimitOn`, `showComplete`, `duplicates`, `types` and `queues` are also checked again on load, a wrong value falling back to the default. `load()`/`update()` keep only `folders` entries with a category name and an absolute string path. `scheduleAt` is gone (it moves into the main queue).
Not saved: `startup` is whether the Startup shortcut exists; `whenDone`, the countdown and the running queues are in memory only.

## HTTP API (`server.js`, 127.0.0.1:9614)
Routes match the path without the query string. `GET /api/ping` · `GET /api/state` → `{settings (+ startup), downloads, queues (with running, waiting, active, total), whenDone (the status bar's choice), powerOp (what the running countdown does, null when none), powerAll (that countdown is "When all downloads finish"), powerIn (seconds left or null), exts (every file type in settings.types), categories (settings.types), open}` · `POST /api/add {url, name?, title?, headers?, scheduled?, queue?, quality?, format?, confirm?, description?}` (`quality`/`format` only for YouTube links; `confirm` adds it as `pending`; `scheduled` puts it into `queue`, default `main`) · `POST /api/formats {url}` → `{title, options}` (YouTube single-video links; cached 15 min) · `POST /api/confirm {id, action: start|later|cancel, path?, quality?, format?, remember?, description?, replace?, rememberDuplicates?, queue?, startQueue?}` · `POST /api/settings {..., speedLimitOn?, duplicates?, showComplete?, types?, clipboard?, startup?, whenDone?}` → the settings · `POST /api/queues {op: add|update|remove|start|stop, id?, name?, …queue fields}` · `POST /api/action {id, op: pause|resume|url|describe|limit|whenDone|queue|up|down|remove|removeFile|folder|open, url?, description?, kb?, value?, queue?}` (`open` runs a finished file with its default app) · `POST /api/open` (show the window), `POST /api/pause-all`, `POST /api/quit` (answers, then saves `state.json` and exits).
- **`open`.** `POST /api/open` adds 1 to a counter that `/api/state` returns as `open`; the native app shows its main window when it rises (tray Open, the extension popup's Open Glide). The engine has no window of its own.
- **App presence.** The engine remembers when `GET /api/state` was last called without an `Origin` header (the native app polls every 700 ms). `POST /api/add` with `confirm: true` while that was more than 5 s ago → 503 `{error: "<name> is not open. Start it from the Start menu."}`: a pending download would wait for a window nobody shows.
- The HTML pages, `/favicon.ico` and `/api/browse` are gone: the native app has its own windows and Windows' Save dialog.

## Windows integration (`server.js`)
- **Start with Windows.** `startup: true` writes `<name>.lnk` into the user's Startup folder through PowerShell (`WScript.Shell`): target `<app>\<name>.exe` (the native app), arguments `--tray`, working folder the app folder. `--tray` starts the tray icon without a window. The exe path is fixed, also when the server runs under `npm start`, so the shortcut only works after `install.cmd`. `false` deletes it. The paths go to PowerShell as environment variables, so no quoting can break the command. `FASTDL_STARTUP` replaces the Startup folder (tests).
- **Open when done.** `mgr.opener` opens the file with explorer, as the Open action does (a download's own `whenDone: 'open'`).
- **Sleep / shut down** (`mgr.power`, at the end of any countdown: the global one, a download's or a queue's). `shutdown /s /t 0`: any other timeout implies `/f`, and without `/f` an app with unsaved work can stop the shutdown. Sleep uses `[System.Windows.Forms.Application]::SetSuspendState('Suspend', $false, $false)`, because `rundll32 powrprof.dll,SetSuspendState` hibernates on PCs that have hibernation on.

## Desktop app (`app/`, `desktop.js`, `install.js`)
Two programs in the app folder:
- **`<name>.exe`, the native app** (C# WinForms, `app/`, compiled by `app/build.js` with Windows' own .NET Framework `csc.exe`): the windows, the tray icon, the one-instance rule. It polls `/api/state` every 700 ms and starts the engine when it does not answer: `<name> Engine.exe` from its own folder, else `node desktop.js` (development). Design and behaviour: `docs/NATIVE_UI.md`.
- **`<name> Engine.exe`, the engine** (`desktop.js` `start()`): asks `GET /api/ping`. FastDL answers: exit 0. Connection refused: import `server.js`. Anything else: error "port used by another program". It has no window and no tray.
- **Brand.** `brand.json` (`name` "Glide", `icon` "assets/logo.ico") is the one place for the app's name and icon: both exe names, version info, window titles and texts, tray tooltip and menu, shortcut names. `readBrand()` allows 1–40 letters, digits, spaces and `. _ ( ) + ! -`, not starting or ending with a space or a dot: the name becomes file names, window text and PowerShell input. The extension can't read `brand.json`: its manifest name, popup and context menu hold the name, and `extension.test.js` checks they match. Internal names stay FastDL (User-Agent, `FASTDL_*` variables, ping's `app: 'fastdl'`).
- **Engine exe.** `install.js` builds `<name> Engine.exe` as a Node single executable application from the `node.exe` that runs it, without npm tools. `--experimental-sea-config` makes the blob from a small launcher. The copy of node.exe drops its Authenticode signature (it would no longer match). kernel32 `UpdateResource` (PowerShell `Add-Type`) replaces all resources with node.exe's manifest, our version info (name, version from `package.json`), the icons and the `NODE_SEA_BLOB` RCDATA. Then the SEA fuse becomes `:1` and the PE subsystem 2 (Windows GUI), so no console window. postject would do the same resource write and fuse flip, but needs npm. The launcher imports `desktop.js` from the exe's folder, so engine code changes need no rebuild, and shows startup errors in a message box. Rebuild after a brand or Node change.
- **App exe.** `compileApp()` (`app/build.js`): winexe, x64 (PE32+), the brand icon (`/win32icon`, every .ico image as an RT_ICON), `app.manifest`, and the name and version as assembly attributes. Rebuild after a change in `app/`.
- **Icon.** The .ico goes into the engine exe as is: each image becomes an RT_ICON resource and the directory an RT_GROUP_ICON (`iconResources()`). Its images are PNGs, which Windows reads. The native app loads the same file with user32 `LoadImage`, because .NET Framework's `Icon` class draws PNG images as noise.
- **Install.** `install.cmd` runs `node install.js`. It refuses while the engine answers on the port or `<name>.exe` runs (`tasklist`; Windows can't replace a running exe), builds both exes, writes `<name>.lnk` (target the native app) to the Start menu Programs folder and the Desktop (`[Environment]::GetFolderPath`, so a OneDrive desktop works), re-creates the Startup shortcut (native app `--tray`) if one existed under the old or new name, records the name in `installed.json`, refreshes the icon cache (`ie4uinit -show`) and starts the native app. If `installed.json` has another name, that install is removed first. `uninstall.cmd` removes the three shortcuts, both exes and `installed.json`; `state.json` stays.
- **Setup (releases).** `node build-installer.js` makes `dist\<name>Setup.exe` and its `.sha256` ("<hash>  <file>", as limewheel's). It stages what runs, without tests, sources or state: `<name>.exe`, `<name> Engine.exe` (the same `build()`), the engine's modules (`desktop.js` and its `./x.js` imports, followed through), `package.json` (`"type": "module"`), `brand.json`, `assets/`, `extension/`, `LICENSE`, a README.txt and Node's license (`licenses\node-LICENSE.txt`). It zips them with Node's zlib and compiles `installer/*.cs` with the app's sources (its look) and the zip as a managed resource. The setup installs per user, no admin: `%LOCALAPPDATA%\Programs\<name>` (or an earlier install's folder), Start menu shortcut, optional desktop and Startup (`--tray`, the app's own "Start with Windows" shortcut) ones, the Settings > Apps entry (HKCU Uninstall key: DisplayName, DisplayIcon, DisplayVersion, Publisher 1949-2005, InstallLocation, UninstallString, QuietUninstallString, EstimatedSize, NoModify, NoRepair) and `Uninstall <name>.exe`, a copy of itself. yt-dlp, FFmpeg and Deno come from winget (`winget install -e --id yt-dlp.yt-dlp`, whose dependencies are yt-dlp.FFmpeg and DenoLand.Deno; a tool still missing after it gets its own id), found as `ytdlp.js` finds them; they are not bundled, so they stay current. An upgrade overwrites the files and keeps `state.json`. Glide running from the install folder (its exes, by image path) blocks install and uninstall; "Quit <name>" posts `/api/quit` (the engine saves the list) and then ends the window, which keeps nothing unsaved. Uninstall removes only what the zip lists, the uninstaller (cmd deletes it once it has exited), the shortcuts that point at this install, the key, and `state.json` when asked: never anything else, so downloads stay even inside the install folder. Test hooks: `GLIDE_SETUP_DIR`, `_PROGRAMS`, `_DESKTOP`, `_STARTUP`, `_REGKEY`, `_WINGET`, `_SHOTS`, and `--quiet` (exit 0 ok, 1 error, 2 running, 3 tools missing).

## Phone access (`remote.js`, port 9615)
Off by default. When on (settings.remote.enabled), a second server listens on all interfaces at 9615 for the phone's page and API; the 127.0.0.1:9614 API is unchanged and still the only one the app and extension use.
- Pairing: `POST /api/remote/pair` (local API only) makes a 128-bit secret valid 10 minutes, once, and answers the link `http://<LAN IP>:9615/#pair=<secret>` with its QR grid (`qr.js`). The secret rides in the #fragment, so it is in no request line or log. The page posts it to `/api/pair` and gets a 256-bit device token, kept in its localStorage; state.json keeps only the token's SHA-256 (settings.remote.devices: id, name from the User-Agent, added, last seen). Wrong secrets: 10 a minute at most, then 429.
- Every other phone call needs `Authorization: Bearer <token>`: `GET /api/state` (the list, without pending ones), `POST /api/add` (url, and quality for video pages; queued at once, no Download File Info), `POST /api/action` (pause, resume, remove only), `POST /api/ticket` (a finished file's one-time link, 60 s) then `GET /file/<ticket>` (attachment).
- The Host header must be an IP address and the port (no DNS names: rebinding). Token hashes never leave the engine (`/api/state` and `/api/settings` drop settings.remote); `/api/remote` lists devices without them. Removing a device ends its token at once.

## Security model
- Binds 127.0.0.1 only. `Host` must be `127.0.0.1:PORT` or `localhost:PORT` (DNS rebinding).
- The native app sends no `Origin`. `Origin`, when present, must be a browser extension (or the engine's own origin). Other websites get 403.
- Extension origins may only use `GET /api/ping`, `POST /api/add`, `POST /api/formats` (it only reads a YouTube video's list; keys are validated before yt-dlp sees them) and `POST /api/open` (it only shows the window); anything else is 403, including `/api/confirm` and `/api/state`: only the native app's Download File Info dialog picks the folder. Any installed extension can reach the app, and settings (download folder, Start with Windows, sleep/shut down) or `open` would let it plant and run files. The Startup shortcut's target is fixed; nothing from the request goes into it.
- Finished files get the Mark-of-the-Web (`:Zone.Identifier` stream, `ZoneId=3`, referrer, URL without credentials) on Windows, like browsers do, so SmartScreen and Office Protected View still apply. Write errors are ignored (FAT/exFAT).
- Cookies come from the extension, are sent only to the host they were captured for, also across redirects, and are dropped from the state once the download is done.
- Header allowlist: cookie, referer, user-agent. The default User-Agent is honest.
- File names can't leave the download folder (`sanitize()`).

## Extension (`extension/`)
Takes over browser downloads when the app is running (toggle in popup), "Download with Glide" context menu (for both, the native app shows the Download File Info window), media grabber (video/audio responses > 512 KB and HLS playlists per tab, badge count), sends cookies + referrer, never the browser UA. On a YouTube video page the popup shows **Download this video** (the format is picked in the Download File Info window). YouTube cookies are never sent to the app.
- **Video panel** (`content.js`, in every frame, so embedded players work too), IDM's download panel. Hovering a rendered `<video>` of at least 200x112 px shows a panel 8 px inside its top-right corner: a grip, **Download this video** (the app icon's tile, as on the toolbar and in the tray: assets/logo.svg's 16 px rendering as inline SVG, fixed colors), **?** and **×**. It hides 1.5 s after the pointer leaves the video and the panel, and follows scroll and resize. The pointer is matched by position, because players put their controls over the `<video>`. It sits in a closed shadow root on a fixed host (z-index 2147483647), so page CSS and scripts can't reach it, and only trusted clicks (mouse or keyboard) count. Not shown over fullscreen video: only the fullscreen element is drawn there. **?** opens a help box under it (how to turn it off in the popup, how to move it); OK, Esc or a click elsewhere closes it. **×** hides it at once on that video until the page's URL changes (`dismissed`: video → its YouTube video's URL, else the page's, because YouTube reuses one `<video>`). **Drag:** a trusted press that moves 4 px moves the panel (the pointer is captured only then, so a short press still clicks the button under it); the offset holds for the page; `panelAt()` keeps the panel in the window; a double-click on its edge (grip or padding) puts it back. On a YouTube page's own player (`#movie_player`) the panel's first show also asks for the format list in the background (`{type: 'formats'}`, once per video), so a click often finds it ready: yt-dlp takes about 3 s, about 8 s after a YouTube player update. One trusted click on **Download this video** sends. Feed previews (YouTube home, search, channel): the inline preview `<video>` sits over its thumbnail, so `targetOf()` takes the first watch link (`ytWatchUrl()`, without playlist parameters) under the preview's center (`elementsFromPoint`, worked out again only when the `<video>`, its place or the URL changes) and the preview gets the same format list as a watch page; its list is prefetched only when the pointer reaches the button, and × hides the panel for that previewed video only. On YouTube videos (the page's own player on `isYouTubePage()` pages, same as `isYouTubeVideo()`, or a preview with its watch link) the button has a chevron and the click opens a format menu under the panel instead: "Getting formats…", then groups [MP4] Video / [WEBM] Video / [M4A] [MP3] Audio under sticky headers (a white chip per file format the group offers; the header stays pinned while its rows scroll under it, and `scroll-padding-top` keeps the focused row clear of it), rows with label, tag and real size, and under them, as in IDM, the exact file name that row saves (`fileName()`: engine.js `sanitize(title + extOf(key))`, title from the formats answer, else the page's): whole, at 13px, wrapped over as many lines as it needs and never cut, `dir="auto"`. The menu is 440px wide, narrower when the panel is near the window's left edge (`--room`: the panel's right edge), and at most min(480px, 70vh) high, scrolling beyond; on an error, the message and "Download anyway" (no format). Up/Down wrap, Esc closes, a click elsewhere closes; the page's keys don't see the menu's keys. The menu asks `background.js` `{type: 'formats', pageUrl}`. It first starts `POST /api/formats` (one request per page while the worker lives; failures asked again), which also warms the app's 15-min list for its Download File Info window. Then it reads the formats YouTube's own player in the page already has, as IDM does: `chrome.scripting` (`scripting` permission) runs `playerData()` (`common.js`) in the sender's frame, in the page's MAIN world; it takes the `.html5-video-player` whose `getVideoData().video_id` and response's `videoId` are the page URL's video id (watch, Shorts and feed previews alike) and returns plain data from `getPlayerResponse()` (title, length, live, adaptive formats: itag, mimeType, contentLength, size, fps, bitrate, HDR, DRC, audio track). `optionsFromPlayer()` turns that into the same list as `formatOptions()` (checked against real captures of the same videos in `fixtures/youtube-player.json`): numeric itags only (the page is not trusted), formats without contentLength left out, DRC copies and non-default audio tracks left out, an itag listed twice keeps its first entry (as yt-dlp), best audio and video by bitrate; with several audio tracks the ids get yt-dlp's suffix (`140-22`: the default track is the last of n). It answers at once (a few ms) when that gives at least one option; otherwise (no player for that id, an error, live, nothing usable) it answers with the app's list. A pick sends the page URL and title kept from when the menu opened (YouTube changes pages without reloading) with `format`. The content script sends `{type: 'video', src, pageUrl, title, format?}`; `background.js` takes it only from this extension with a tab, checks every field, and `pickMedia()` (`common.js`) decides: YouTube page → the page with the quality, format and title (`format` checked against `FORMAT_KEY`); http(s) `src` → that file with the page as referrer; blob:/MSE players → the tab's first grabbed HLS playlist, else its biggest video file; nothing → "No video found yet. Play it for a few seconds, then try again." The background adds it with `confirm: true`, and the native app shows the Download File Info window. The label shows "Sending…", then for 2.5 s "Sent to Glide ✓" or the error. The popup switch "Show download button on videos" (`overlay`, on by default) removes it from open pages at once.
- **Updates without reloading tabs.** An update or ↻ cuts the open tabs' copies of `content.js` off from the extension. `onInstalled` (install, update) injects the new `content.js` into every frame of each open http(s) tab (`chrome.scripting`; restricted and discarded tabs refuse, ignored). The new copy runs in a new JS world and first dispatches `glide-start-<extension id>` on the shared `document`; an older copy that hears it removes its panel and stops all its handlers and timers, so the tab keeps exactly one working panel and the page is not reloaded. A tab that already loaded the new version gets the file a second time in the same world: the top level only uses `var` and `function` (no "already declared"), and `globalThis.glideMain` keeps the running copy. A copy nobody replaces still answers a click with "Reload the page and try again." Copies from before this change have no teardown: they need one reload of the tab.
